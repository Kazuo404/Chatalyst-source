# Estado de auditoría — 2026-07-15

Esta revisión contrasta el código, los recursos, los artefactos generados y la documentación de
Chatalyst 1.0.0. No sustituye una prueba de carga ni una matriz real de servidores.

## Resultado reproducible

- `./gradlew clean test build releaseJar --no-daemon`: 398 pruebas, 99 suites, 0 fallos y 0
  omitidas; también genera el artefacto final ofuscado.
- `./gradlew build`: compila Paper, Velocity, Bungee y el código común de proxy.
- `./gradlew releaseJar --rerun-tasks`: ProGuard termina correctamente; el jar final conserva
  `plugin.yml`, `velocity-plugin.json`, `bungee.yml` y los tres entry points.
- Los YAML incluidos y las claves de idioma inglés/español pasan sus validaciones de build.
- OSV no reportó vulnerabilidades conocidas para las versiones directas consultadas el día de la
  revisión: SQLite JDBC, MySQL Connector/J, Nashorn, ProGuard y JUnit.

## Hallazgos corregidos en esta revisión

- La wiki describía la traducción como opt-out y todavía mencionaba `Only_When_Mixed`; el runtime
  actual es opt-in y esa opción ya no existe. La documentación ya coincide con el código.
- El sitio omitía LibreTranslate, la detección dinámica de idiomas y la limitación de borrado de
  líneas traducidas. Se añadieron junto con la advertencia de privacidad.
- La tabla de compatibilidad ahora distingue Java 21 (Minecraft hasta 1.21.11) de Java 25
  (Minecraft 26.1+), según la documentación vigente de Paper.
- CI ahora construye también `releaseJar`, no solo el jar de desarrollo.
- La migración desde `config.yml` monolítico ya no sobrescribe nada si no puede crear antes su
  backup, y la carga previa es estricta.
- Se migraron los bans de perfil y la construcción de URL a las APIs vigentes. Los dos usos
  internos inevitables (`PlayerEditBookEvent#getSlot` y `Bukkit#getUnsafe` para toasts) quedan
  aislados, documentados y con degradación segura.

## Hallazgos corregidos en la tercera pasada

Los dos primeros se reprodujeron contra las clases compiladas antes del cambio; los demás se
confirmaron siguiendo sus transiciones y rutas de error. Todos cuentan ahora con corrección y,
cuando el núcleo puede aislarse de Bukkit/Vault, una regresión determinista.

1. **Alta — traducción con URL inválida puede tragarse el chat.** `TranslationService` elimina
   la misma clave de `inflight` desde un `whenComplete` que puede ejecutarse sincrónicamente dentro
   de `ConcurrentHashMap.computeIfAbsent`. Java lanza `IllegalStateException: Recursive update` y
   `ChatListener` ya había cancelado el evento para tomar control de la entrega.
2. **Alta — confirmación obsoleta en negociación y trade directo.** La comprobación de “ambos
   aceptaron/listos” se separa del cierre atómico. Otra región puede modificar la oferta, reiniciar
   las confirmaciones y aun así el primer hilo cierra usando la oferta nueva. El modelo compilado
   permitió reproducir `stale execute=true` con `bothReady/bothAccepted=false`.
3. **Alta — los créditos fallidos de Vault no detienen la entrega.** Mercado, subasta y trade
   comprueban el retiro, pero ignoran el resultado de varios `deposit`, incluida una compensación.
   Un proveedor de economía que rechace el abono puede dejar dinero retirado, entregar los items y
   anunciar éxito.
4. **Alta en Folia — trade directo accede a dos inventarios desde una sola región.** La ejecución
   consulta el espacio de ambos jugadores desde el hilo de uno de ellos y entrega más tarde en dos
   schedulers. El inventario puede cambiar entre comprobación y entrega; el sobrante se tira al
   mundo aunque el contrato del método afirma que la operación cancela sin drops.
5. **Media — `reveal` no está ligado al espectador.** El contenido renderizado se guarda solo por
   id de mensaje; cualquier jugador que conozca ese id puede pedirlo. El borrado de moderación
   elimina la firma, pero conserva el contenido revelable, sin TTL.
6. **Media/alta — limpiezas no condicionales pueden borrar datos concurrentes.** Correo y amigos
   usan CAS para una transición y después ejecutan `remove` si una lectura parece vacía. Una nueva
   entrada creada entre ambas operaciones puede ser eliminada. Aceptar/denegar solicitudes y los
   fallbacks de correo/tickets vuelven además a `get` + `put`, que puede pisar cambios cross-server.
7. **Media/alta — expiraciones pueden borrar una sanción recién aplicada.** Mutes, bans y decay de
   warning points leen un estado viejo y luego eliminan cache/store sin comparar el valor observado.
   Una sanción nueva que se cruce con esa limpieza puede desaparecer.
8. **Media — `/chatlog <fecha>` hace E/S completa en el hilo del comando.** Antes de responder
   fuerza `flush()` y recorre todo el archivo diario. La memoria está acotada, pero un log grande
   puede pausar el tick principal o la región del staff.
9. **Riesgo de configuración alto — forwarding sin secreto continúa fail-open.** En modo nativo o
   Bungee se registra el canal aunque no haya autenticación; el propio runtime advierte que un
   cliente modificado puede forjar paquetes. Redis ya bloquea el transporte con secreto inválido,
   pero los otros modos no aplican la misma política.

La implementación sella confirmaciones y oferta indivisiblemente, compensa las transferencias
económicas con un ledger de reintegros, accede a cada inventario solo desde su scheduler de entidad,
liga `reveal` al espectador y añade borrado condicional al contrato de `Store`. El log diario se lee
en el scheduler asíncrono y los transportes de plugin messaging quedan fail-closed sin secreto.

## Hallazgos corregidos en la cuarta pasada — 2026-07-16

La revisión se amplió de los nueve hallazgos iniciales a sus límites de persistencia, recuperación
tras crash, ejecución Folia y comunicación cross-server. Además de corregir cada ruta encontrada,
se añadieron pruebas de regresión para las primitivas que pueden aislarse de Bukkit/Vault.

1. **Alta — un crash podía duplicar, perder o reasignar mal items de mercado/trade.** Publicación,
   ofertas y entrega usan ahora markers persistentes y journals de escrow. Los drafts y claims no
   tiran sobrantes al mundo; se conservan en un alijo durable y deduplicado.
2. **Alta — una llamada Vault completada no podía distinguirse de una interrumpida.** Ventas,
   subastas y trades tienen un WAL `PREPARED/PROCESSING/PAID/UNPAID`. `PROCESSING` nunca se repite
   automáticamente: un operador verifica la economía y resuelve con `/market settlements` o
   `/trade settlements`. Los trueques solo de items también pasan por el WAL.
3. **Alta — varios CAS eran solo cambios de cache.** `Store` expone operaciones durables que
   revierten la cache si falla el flush. Correo, solicitudes de amistad, tickets, reportes,
   sanciones, staff mode, migraciones y ledgers consumen esas operaciones sin fallback `get+put`.
4. **Alta — MySQL compartido podía servir cache indefinidamente obsoleta sin Redis.** El arranque
   falla cerrado si no conecta y un poll asíncrono configurable reconcilia altas, cambios y bajas
   remotas sin pisar escrituras locales pendientes.
5. **Alta en Folia — quedaban accesos a entidades desde otra región.** Renderizado, mensajes
   privados, notificaciones de mercado/trade, reportes, teleports y menús de jugadores se ejecutan
   en el scheduler de la entidad correspondiente o trabajan con snapshots inmutables. La revisión
   de inventario captura una copia en la región del objetivo antes de abrir la GUI del staff.
6. **Alta — el salto Velocity confiaba en el jugador usado como carrier.** El proxy valida ahora
   la identidad solicitante firmada y que siga conectado al backend de origen; el carrier solo
   transporta el paquete autenticado.
7. **Media/alta — la recuperación de staff mode consumía el snapshot antes de guardar.** El
   inventario y el estado durable de vanish se restauran primero y el snapshot solo se elimina
   después. El apagado deja los journals para recuperación en vez de programar tareas de entidad
   que pueden cancelarse; vanish, ignore y clear-warnings ya no anuncian una escritura solo en cache.
8. **Media/alta — movimientos interrumpidos de spam, amistad y reportes podían borrar cambios.**
   El correo usa ids estables y autocura copias inbox/spam; amistades y eliminaciones usan estados
   o journals idempotentes; reportes y conversaciones fallan cerrado si no alcanzan storage.
9. **Media — respuestas permisivas del marketplace podían aceptar licencias ambiguas.** Cada
   proveedor exige ahora su estructura y booleanos de éxito/compra documentados, con regresiones
   para respuestas incompletas.

Los comandos de reconciliación y el comportamiento de MySQL/Redis/fail-closed quedaron reflejados
en las páginas de mercado, base de datos y proxy. Desde el 2026-07-16 `docs/` está versionado en
git, por lo que esta evidencia forma parte del repositorio.

## Hallazgos corregidos en la quinta pasada — 2026-07-16

1. **Alta en Folia — moderación delegada ejecutada desde la región del staff.** `/kick`, `/ban`,
   `/unban`, `/mute`, `/unmute`, `/freeze` y `/vanish <otro>` comprobaban permisos o modificaban
   al objetivo desde otro scheduler. Las autorizaciones y acciones corren ahora en la región del
   objetivo; las respuestas y auditorías vuelven a la del moderador. Notificaciones de amistad,
   perfiles de cabezas y conteo de staff en reportes siguen el mismo modelo.
2. **Media/alta — preferencias confirmadas antes de persistir.** Nick, tag, color/estilo de chat,
   toggles, canal escrito/escuchado/silenciado, frecuencia, reglas e item-name podían actualizar
   cache/UI y anunciar éxito antes de que YAML/SQL fuese durable. Las mutaciones revierten o no
   publican estado si falla el flush/CAS, y los comandos muestran el error.
3. **Media/alta — cuota de `/itemname` no atómica.** Dos usos concurrentes podían superar el
   límite y un fallo de storage podía renombrar sin consumir una cuota durable. La reserva se hace
   ahora con CAS antes de tocar el item.
4. **Media/alta — acciones de correo con GUI obsoleta.** Aceptar/rechazar, quitar amigos,
   bloquear/desbloquear y privacidad ocultaban fallos de persistencia. Además, las solicitudes se
   identificaban por índice: un cambio remoto podía desplazar la lista y aceptar a otra persona.
   La GUI captura la identidad estable y cada resultado distingue ausente, aplicado y fallo.
5. **Media — secuencia de reportes podía retroceder.** Dos creaciones locales podían escribir
   `$seq` fuera de orden y el ajuste local separaba `get` de `set`, permitiendo retroceder el
   contador y reutilizar un ID. El acumulador y el hint son atómicos/monotónicos, y el arranque
   siempre toma el máximo entre contador y reportes reales.
6. **Media — historial de mercado perdía entradas concurrentes.** El append era `get + put`
   diferido. Ahora compone y limita las líneas mediante CAS durable, sin sobrescribir otra compra
   confirmada desde una ruta concurrente.
7. **Media — configuración inválida alteraba seguridad.** `NaN`/infinito o valores fuera de rango
   podían desactivar el delay/similitud anti-spam; los switches de controles e invisibles del
   sanitizer no eran independientes; retenciones negativas vaciaban el historial. Los valores se
   normalizan y cada categoría se filtra por separado.
8. **Media — nombre de formato sin confinamiento.** `Chat.Default_Format` y overrides aceptaban
   separadores y `..`, permitiendo leer YAML fuera de `formats/` por error de configuración. Solo
   se admiten identificadores simples y cualquier valor inválido cae a `chat`.
9. **Media — desmute/desban/unfreeze confundían ausencia con fallo.** Los comandos ya no dicen
   “no existe” cuando falló el CAS/flush. El espejo nativo de Paper al desbanear se captura y el
   registro durable se restaura condicionalmente si ese paso falla.

El análisis de crash logs locales no encontró una caída atribuible a Chatalyst: el log más reciente
falló antes de crear hilos Java por falta de memoria nativa. El proyecto no contiene todavía un
harness de Paper/Folia o Testcontainers, por lo que el smoke test real sigue siendo riesgo residual.

## Riesgo residual y siguiente búsqueda

1. Ejecutar smoke tests en Paper/Purpur 1.21.1, 1.21.11 y 26.2, además de Folia, usando una licencia
   de prueba y verificando enable, reload, chat y shutdown limpio. El recorrido concreto está en
   el [checklist de smoke test](smoke-test.es.md).
2. Añadir integración con SQLite y MySQL reales; las pruebas actuales validan concurrencia y CAS
   con dobles, no el driver ni una caída de red.
3. Automatizar recorridos GUI/comandos para staff, correo, mercado, anuncios y editor de formatos.
4. Actualizar dependencias en un PR separado y medir compatibilidad: el proyecto usa SQLite JDBC
   3.46.1.3, MySQL Connector/J 8.4.0 y Shadow 9.0.0-beta2, mientras al auditar existían releases
   estables más recientes. No se detectó un CVE directo, por lo que conviene hacerlo con pruebas,
   no como cambio incidental.
5. Revisar los cargadores YAML restantes que aún usan la API tolerante de Bukkit y las escrituras
   directas no atómicas fuera del nuevo helper compartido.
