Chatalyst

Chatalyst is a self-contained chat plugin for Paper and Purpur. It formats every message, routes it through channels, filters unwanted content, and gives staff the tools to keep chat healthy.

It replaces a full chat stack without mandatory dependencies. Its own Discord bot starts with Chatalyst, while optional plugins such as LuckPerms, PlaceholderAPI, WorldGuard and Parties are detected automatically.

Chat without a stack of plugins

Build MiniMessage formats with rank data, hover cards, click actions and held-item previews. Route the result through global, local, world, region or party channels, then connect those conversations across a proxy when needed.

Public chatFormats, channels, mentions, grammar, anti-spam, multilingual rules and opt-in per-viewer translation in one pipeline.
Private chatInstant messages, replies, persistent ignores, personal PM toggles, social spy and optional mail fallback.
Offline mailA GUI inbox, book-based messages, friends, spam controls and configurable join notifications.

A richer player experience

Players can choose chat colors and styles, build a nickname, rename an item, toggle mentions or announcements, mark themselves AFK and browse the economy leaderboard. Chatalyst can carry that identity into chat, tab, nametags and supported third-party commands.

Moderation with context

Staff get persistent mutes, warning points, soft mute, social spy, a player-management GUI and daily chat history. Reports behave like tickets: they can be claimed, prioritized, discussed, resolved, rejected or reopened, with optional Discord staff workflows.

From one server to a network

Store data in YAML, SQLite or MySQL. A shared MySQL can make nicks, mail, mutes and tickets network-wide, while Redis delivers signed cache and channel updates between backends. Velocity and Bungee bridges are also available.

Uses the plugins you already trust

Chatalyst runs standalone with its own Discord bot, then detects LuckPerms, Vault, PlaceholderAPI, WorldGuard, Parties, ItemsAdder, Nexo, TAB, EssentialsX, dynmap, voice-chat plugins and PacketEvents when they are present.

About

Overview

Chatalyst is a modern, self-contained chat plugin for Paper and Purpur (1.21.1 – 26.2). It formats every message, routes it through channels, filters advertising and profanity, and gives moderators the tools to keep chat clean.

It aims to replace a full chat suite on its own, with no ProtocolLib and no mandatory dependencies. Its embedded Discord bot needs no DiscordSRV or webhook, and optional server plugins are detected automatically.

FormattingMiniMessage formats, hover and click, per-rank colors, an in-game editor.

Installation

Installation

Drop the jar in and start the server. Everything beyond a Paper-based server is optional.

  1. Stop the server. Replacing a running jar can be read mid-write.
  2. Place Chatalyst-1.0.0.jar in your plugins/ folder.
  3. Start the server once so plugins/Chatalyst/ and its configuration files generate.
  4. If you received a signed license key, set it under License.Key in config.yml. Marketplace-watermarked builds identify the buyer automatically instead.
  5. Restart and check the console for the Chatalyst license banner. Then edit the configuration and run /chatalyst reload.
Network access

Paper downloads Chatalyst's declared runtime libraries (Nashorn, SQLite and MySQL drivers) the first time they are missing. Marketplace-watermarked builds also need to reach the marketplace verification API on every startup; signed-key builds verify offline.

Optional plugins

Nothing else is mandatory. Chatalyst detects supported plugins on startup and enables only the matching bridge. Use the integration reference to decide what belongs on your server.

Tip

With TAB installed, /nick changes show up in the tab list automatically, and TAB configs can use %chatalyst_nick% (colored), %chatalyst_nick_plain% and the other Chatalyst placeholders without PlaceholderAPI.

Name above the head

The classic nametag only supports one solid color (a Minecraft protocol limit — no gradients or bold there). Two options: add %chatalyst_nickcolor% at the end of tagprefix in TAB's groups.yml to color the name with the player's /nickcolor (gradients use their first color), or enable Nametag.Fancy in the config to replace the vanilla name with a floating text that renders the full nick style, gradients and bold included. With TAB, the fancy mode also needs scoreboard-teams → invisible-nametags: true in TAB's config.

Network services

Redis is not a gameplay dependency. It is an optional signed pub/sub transport for cross-server channel delivery and cache invalidation. MySQL can make persistent player and moderation data network-wide; Velocity or Bungee bridge jars provide native proxy transport.

Tip

After adding or removing an integration, perform a full restart and read the startup module summary. A configuration reload cannot change the server's plugin dependency graph.

Upgrading

Updating to a new version is a jar swap.

  1. Stop the server.
  2. Replace the old jar with the new one.
  3. Start the server. New config keys are added automatically; your existing values are kept.
Note

A code change always needs a full restart, not /chatalyst reload. Reload only re-reads the YAML files.

Installation

Proxy

Chatalyst can sync a channel across a Velocity or BungeeCord network using legacy plugin messaging, a native proxy bridge, or Redis pub/sub.

Proxy:
  Enabled: true
  Mode: redis

Then mark any channel you want forwarded network-wide:

Channels:
  List:
    global:
      Proxy: true

Messages in that channel are delivered to players on every connected server. Local channel types (frequency, world, region and party) stay local by design.

Velocity setup

  1. Install Chatalyst on every backend server (lobby, survival, ...). Your license key covers all of them.
  2. For native mode, place the same signed universal Chatalyst-<version>.jar on every backend and on Velocity or BungeeCord. Each platform loads only its own isolated entry point. For Redis mode, configure the same Redis server and the same Redis.Shared_Secret on every backend. For legacy mode, keep bungee-plugin-message-channel = true in velocity.toml.
  3. Enable Proxy in the Chatalyst config of each backend, choose the same Proxy.Mode, and mark the channels to forward.

Network packet authentication

Native and legacy plugin messages use HMAC-SHA256, timestamps and a bounded anti-replay nonce cache. With Velocity modern forwarding, every backend and the universal proxy jar automatically derive a protocol-specific key from the existing forwarding secret, so no additional key has to be copied.

Proxy:
  Network_Secret: "" # automatic on modern Velocity

BungeeCord native mode has no forwarding secret. Set the same random value (16+ characters, 32+ recommended) in Proxy.Network_Secret on every backend and in the proxy's plugins/chatalyst/network-secret.properties. An explicit value overrides automatic derivation; a non-empty short value fails closed and blocks forwarding. Restart the complete network after changing it.

Warning

Redis mode requires Redis.Shared_Secret: a long random string (16+ characters), identical on every backend. Every message is signed with it (HMAC + anti-replay), so only your own servers can publish to the channel — without it, Redis sync stays disabled. Enable Redis.TLS whenever Redis is reached over a network.

Note

A chat plugin cannot run only on the proxy: since Minecraft 1.19 chat is cryptographically signed by the client, so a proxy cannot modify or cancel messages without breaking the signatures — formatting, filters, GUIs and item features must live on each backend. Every network chat plugin works this way.

Warning

Plugin messaging travels over player connections: cross-server forwarding needs at least one player online on each end. Empty servers simply catch up when someone joins.

Network operations center

The administration GUI can show every registered backend, its live population and a paginated recent-chat timeline. Staff inspect a server without connecting to it. The monitor keeps only a bounded in-memory history of public and channel chat handled by Chatalyst; it never captures commands, passwords, private messages or mail.

Network_Admin:
  Monitor:
    Enabled: true
    History_Per_Server: 100
    Retention_Minutes: 60
  Announcements:
    Enabled: true
    Max_Message_Length: 512

The native Velocity/Bungee bridge automatically supplies topology, player counts and this backend's exact registered identity. Redis-only mode can still relay monitored chat and announcements without carrier players, but it only discovers servers through observed activity.

Proxy:
  Enabled: true
  Mode: native
  Server_Discovery:
    Mode: auto
    Manual_Server_Id: ""
Automatic identity

In auto, the proxy answers only the originating backend with its exact registered name when a player connects; no server list or ID must be copied. Before that first carrier, Chatalyst temporarily uses the database ID, Redis ID or port fallback. Choose manual and set Manual_Server_Id for legacy, Redis-only or deliberately fixed setups. Storage and Redis IDs are never renamed by discovery.

Live feeds and permissions

Staff can mirror up to two permitted server chats at once from /cht admin. Left-clicking a server opens its bounded timeline; right-clicking toggles its live feed. LuckPerms can grant only selected backends with chatalyst.admin.network.monitor.server.<server>. Restricted channels still require their normal channel permission or an explicit chatalyst.admin.network.monitor.channel.<channel> override.

Live staff directory

The administration GUI lists staff by priority tier with their current backend and world. With chatalyst.admin.staff.teleport, one click follows a remote staff member through the native proxy bridge and teleports to their exact location after the destination backend validates permission again. Presence is memory-only, refreshes every ten seconds and expires automatically.

Players by server

Choose a permitted backend such as survival and see only its current players. Every head shows username, LuckPerms/Vault rank, Vault balance, world, game mode, ping and AFK state; clicking it connects through the native proxy bridge and teleports to that player. Vanished players are never published. Access is split between chatalyst.admin.players.directory, chatalyst.admin.players.teleport and per-server nodes such as chatalyst.admin.players.server.survival.

Natural private support

Players can ask naturally — any admin?, hay alguien del staff? or necesito un helper — without learning an @ syntax. Chatalyst matches a whole configured rank or team word plus help intent, removes the request from public chat, and sends a clickable Reply action across the proxy.

Every request starts with helpers, then advances through mod, admin and owner until somebody replies. The proxy arbitrates simultaneous clicks so only the first permitted staff member opens the private session; everyone else is told who is handling it. Player and staff then type normally, but only those two receive the conversation. Staff uses /support close to finish and the player returns to general automatically.

Installation

Discord

Chatalyst includes its own low-latency, two-way Discord bot. It starts and stops with the plugin, so DiscordSRV, a separate process and chat webhooks are not required.

Create and install the bot

  1. Open the Discord Developer Portal, choose New Application, give it a name and open its Bot page.
  2. Choose Reset Token, copy the bot token and keep it private. It is not the Application ID, Public Key or Client Secret. If it is ever exposed, reset it immediately.
  3. Under Privileged Gateway Intents, enable Message Content Intent. Also enable Server Members Intent when rank sync can run from Discord to Minecraft.
  4. Open Installation, enable Guild Install, use the Discord-provided install link and grant View Channels, Send Messages and Read Message History. Add Manage Roles only for automatic rank sync.
  5. Install the app in your server. Put the Chatalyst bot role above every Discord role it must manage.
  6. Enable Discord Developer Mode, then copy the server and text-channel IDs. Paste those IDs and the token into integrations.yml.
Discord:
  Enabled: true
  Bot_Token: "YOUR_PRIVATE_BOT_TOKEN"
  Guild_Id: "123456789012345678"
  Channel_Id: "234567890123456789"
  Minecraft_To_Discord: true
  Discord_To_Minecraft: true

Restart the server or run /chatalyst reload, then use /chatalyst doctor. A bad token, missing intent or invalid numeric ID is reported without disabling normal Minecraft chat.

Security

Never publish the token or place it in a support log. Chatalyst ignores the old Use_DiscordSRV and webhook settings, preventing two independent relays from duplicating messages.

Check it before you need it

Everything the bot does depends on things no config file can confirm: a permission granted in a menu, a role dragged above another one, an intent ticked in a developer portal. Get any of them wrong and nothing crashes — the bot connects, the config looks right, and features simply do nothing, each failing quietly in its own corner.

/chatalyst doctor discord asks Discord directly and reports what it found: whether the gateway is connected, whether every configured channel is visible and writable, whether Manage Roles and Ban Members are granted when the features that need them are on, whether the linked role sits below the bot, and whether the staff allowlist authorises anybody at all. It only reads — no test message, no test role, nothing to clean up afterwards.

Tip

An empty staff allowlist is the most common false alarm: it authorises nobody, including you, so buttons and commands answer "not authorized" and the feature looks broken.

One ban, both sides

A player banned in Minecraft who keeps their Discord seat is only half-banned — that is where they argue the ban and arrange the alt that comes back. With Ban_Sync, banning an account anywhere closes the door everywhere.

Discord:
  Ban_Sync:
    Enabled: true
    Direction: "BOTH"
    Minecraft_Reason: "Banned on our Discord server"

Which account is which comes from the link, never from a name: an unlinked player is simply not mirrored, because guessing a Discord account from a username is how you ban the wrong person. A temporary ban is shown but never enforced on Discord — a guild ban has no expiry, so mirroring a one-day ban would outlive the punishment by years, since nothing ever comes back to lift it. Only a permanent ban removes the account, and the person is told why in a DM before they are removed, while the bot can still reach them.

Before you enable it

Direction: BOTH means a guild ban also creates a permanent Minecraft ban. The bot needs Ban Members and a role above the people it must ban.

Punishments on the member list

A banned, frozen or muted player who looks identical to everyone else in Discord is a gap the staff fill from memory. Punishment_Roles closes it with roles the bot creates and maintains itself — nothing is prepared by hand.

Roles are expressed in tiers rather than exact days, and that is not a shortcut: a Discord role is shared by everyone wearing it, so its name is one string for all of them and cannot read "30 days left" for one member and "12 days" for another. A role per exact day would need one role per day, against a cap of 250 per guild, with every banned member moved daily. Four tiers give the same sense of how long is left and never churn; the exact time goes in the DM, where it can be personal.

Discord:
  Punishment_Roles:
    Enabled: true
    Refresh_Seconds: 300
    Ban:
      Remove_On_Permanent: true
      Tiers:
        month:
          Name: "Banned · 1+ month"
          Color: "#8B0000"
          Min_Remaining_Seconds: 2592000
        hours:
          Name: "Banned · hours"
          Color: "#FF4D6D"
          Min_Remaining_Seconds: 0   # catches everything else

Tiers are matched widest first, so the last one should be 0 to catch everything else. A punishment matching no tier simply gets no role — and that stays true: the tiers are yours, so removing one keeps it removed across updates. A background pass keeps the roles honest as time runs out, and only contacts Discord when something actually changed.

Note

Renaming a tier leaves the old role behind: the bot only removes roles whose name it currently reads in the config, so anyone still wearing the previous name keeps it. That is deliberate — a role it does not recognise might be one of yours. Delete the old role by hand; the bot recreates what it needs, by name, on the next punishment.

Moderation tools from Discord

Discord.Staff.Handle_From_Discord lets staff work reports from Discord, and report cards carry Claim, Reply, Resolve and Reject buttons that do exactly what the typed commands do — same switch, same channel, same allowed users or roles, because a button is as powerful as the command.

Real moderation tools live behind their own switch, Discord.Staff.Commands_From_Discord, on purpose: closing a report and banning somebody are not the same authority, and one key for both would grant the second by granting the first. They run as the console, only from an allowed channel by an allowed user or role, and the command's own answer comes back to the channel — which is what makes !check and !seen worth typing.

Discord:
  Staff:
    Handle_From_Discord: true    # reports: commands and card buttons
    Commands_From_Discord: true  # !ban, !kick, !check... its own key
    Command_Prefix: "!"
    Allowed_Role_Ids: ["345678901234567890"]

Two kinds of request are refused, with the reason. Anything needing you inside the game (/invsee, /echest, /tpto, /tphere, /vanish, /staff) is meaningless from outside. And /clearinventory is refused for the opposite reason — it would work perfectly, but it is the only tool here that cannot be undone: worn armour and an ender chest do not come back. Asked for by chat, against somebody you are not looking at, a mistyped name stops costing an apology.

Note

Only Chatalyst's own commands ever run: the request is dispatched by its namespaced form, so a label another plugin also owns cannot be what executes. With the staff suite disabled, nothing resolves and the bot says so.

One rank catalog for LuckPerms, Discord and Tebex

The YAML key is a stable, lowercase Rank ID. The same entry owns the exact LuckPerms group, Discord role and optional Tebex delivery settings, so names are not repeated across unrelated lists.

Rank_Catalog:
  owner:
    LuckPerms_Group: "owner"
    Discord_Role_Id: "345678901234567890"
    Discord_Priority: 1000
    Tebex_Enabled: false
    Tebex_Duration: "permanent"
  vip:
    LuckPerms_Group: "vip"
    Discord_Role_Id: "456789012345678901"
    Discord_Priority: 100
    Tebex_Enabled: true
    Tebex_Duration: "30d"
Discord:
  Rank_Sync:
    Enabled: true
    Direction: "BOTH"

Players link safely with /discord link in Minecraft and !link CODE in Discord. Discord can only grant groups declared in this catalog. Higher Discord_Priority wins when a member has several managed roles.

Tebex rank delivery

Keep the official Tebex plugin as the queue owner. In the package commands, use the stable Rank ID:

chatalyst tebex grant {id} vip {transaction}
chatalyst tebex revoke {id} vip {transaction}

Chatalyst resolves vip through Rank_Catalog, verifies the LuckPerms group, deduplicates the transaction and reuses the absolute expiry on retries. Enable this path with Tebex.Enabled: true.

Player rank store

/ranks opens a paginated storefront for players; rename it with Tebex.Shop.Command if that label is taken, and /chatalyst ranks always works as a fallback. Chatalyst never takes a command another plugin already owns, so your shop plugin keeps /shop. Every visible card is defined in YAML with its own MiniMessage name, description, icon, displayed price, order, featured state, optional visibility permission and exact Tebex package URL.

Tebex:
  Shop:
    Enabled: true
Rank_Catalog:
  vip:
    Shop:
      Visible: true
      Display_Name: "<gold><bold>VIP</bold></gold>"
      Icon: "example:vip_icon"
      Price: "$9.99 USD"
      Purchase_Url: "https://your-store.tebex.io/package/1234567"

Selecting a card sends a clickable chat button for that exact rank. Minecraft asks the player to confirm before opening the browser; Chatalyst publishes HTTPS links only and rejects malformed or credential-bearing URLs. Card icons accept vanilla materials or ItemsAdder namespaced IDs, and every store text supports ItemsAdder font images.

Open /chatalyst tebex gui to design a global delivery or a different presentation for each Rank ID. Choose a buyer-only or server-wide audience, then combine chat, toast, title, action bar, sound and safe cosmetic fireworks. The subtle, fancy and silent presets keep every custom text intact.

Rank_Catalog:

Presentations run only after LuckPerms succeeds and the purchase receipt is safely committed. Buyer-only deliveries made while the player is offline appear on their next join, and the feature works even when the Discord bot is disabled.

Reloading

Run /chatalyst reload (short form: /cht reload) after editing most YAML files. It re-reads config, rules, formats, filters and messages live. Adding or removing command aliases, changing proxy mode, editing tags.yml by hand, and Java code changes need a restart; title changes made through the GUI are saved and applied immediately.

Tip

All player-facing text uses MiniMessage. Legacy & color codes are accepted too and converted automatically.

Self-healing config

A broken config.yml does not kill the plugin. On startup Chatalyst validates the YAML: if it cannot be parsed, it rescues your license key, backs the file up as config-broken-<timestamp>.yml, regenerates a valid default and reports the exact line of the error with context in the console. On a healthy config it still warns about unknown keys (typo suggestions included) and invalid values. Run /chatalyst doctor any time to get the same diagnosis in game without touching anything.

Update notices

Chatalyst can check a URL for the latest version on startup (Updates.Check / Updates.Url). It never downloads anything: if a newer version exists it logs a notice and tells admins on join, with an optional clickable Download_Url. Your marketplace's own auto-update handles the file, verifying your purchase.

Staff & moderation

Staff mode (/staff) swaps a moderator into a tidy moderation inventory — its buttons run the same actions as the commands below — and restores their survival items on exit. /staff menu opens a dashboard; /players lists everyone with a right-click per-player menu of presets (mute tiers, kick, freeze, teleport, chatlog).

Freeze reviews (/freeze, /unfreeze) hold a player still while you talk to them. Disconnecting mid-freeze triggers a grace-period, network-aware automatic permanent ban — combat-logging out of a review no longer works, and reconnecting on another backend of the same proxy still counts as present.

Vanish (/vanish) hides a staff member from lists, tab, chat range and other players; operators are always protected as moderation targets, and a non-operator carrying a bypass node cannot be actioned by ordinary staff.

Vanish is for watching: while invisible you cannot break or place, hit anything, open chests or doors, eat, drop, pick up or move your own inventory (Staff_Moderation.Vanish.Observer_Only, four switches, all on). A block that breaks itself gives the vanish away as fast as being seen does — but the real reason is the advantage, since invisible you could mine inside somebody's base or finish off a fight with no possible answer. Damage received is deliberately untouched: an invulnerable vanish turns lava, the void and every trap into a free viewing platform, so walking in where you should not costs what it costs anyone, death and dropped items included. Staff tools are never blocked — the staff-mode kit, Chatalyst menus and the invsee editor are how the watching is done.

Localization

Chatalyst talks to each player in their own language automatically.

Interface messages follow the player's client locale when a matching language file exists. The bundled languages are en_US and es_ES; broadcasts, console output and unmatched clients use the default Locale from config.yml.

Adding a language

Copy lang/en_US.yml to lang/<locale>.yml and translate the values. With Auto_Detect_Language: true, Chatalyst discovers every dropped-in language file and first matches the exact client locale, then any file for the same language; otherwise it falls back to Locale. Command aliases can also carry a Messages_es variant for bilingual replies, so /discord answers in the player's language.

discord:
  Messages:
    - "Our Discord: https://discord.gg/..."
  Messages_es:
    - "Nuestro Discord: https://discord.gg/..."

Live chat translation

A LibreTranslate-compatible endpoint can translate public chat separately for each viewer. Configure Translation.Provider_Url in integrations.yml, enable the service there or from the admin GUI, and let each player opt in with /toggle translate. Both the owner switch and the player preference default to off.

Requests are asynchronous, deduplicated per target language and cached. Only opted-in viewers whose client language differs from the sender trigger a request; the sender, console and everyone else receive the original. If the provider fails or times out, the original text is delivered.

Privacy and signed chat

The provider receives the plain chat text and target language, so prefer a self-hosted HTTPS endpoint and review any hosted provider's retention policy. Translated lines are per-viewer system messages: moderation, logging, Discord and mentions still work, but Minecraft cannot retract those already displayed lines with the staff delete-message X.

Channels

Every player writes in one channel and reads the ones they can access. Five channel types cover any layout.

TypeWho receives the message
GLOBALEveryone on the server, or the whole proxy network
WORLDPlayers in the same world
FREQUENCYRadio users tuned to the same active frequency, with no distance limit
REGIONPlayers sharing a WorldGuard or Chatalyst region
PARTYMembers of the same Parties party

Radio frequency

The built-in local channel is a radio, not proximity chat. A blank Channels.Frequency.Default keeps it off until a player tunes to 10.00–99.99 with /frequency; setting a default tunes new players automatically. The selection is persistent.

/frequency opens the tuner, /frequency 42.50 tunes directly and /frequency off disables reception. /f <message> speaks on the tuned frequency without switching away from the current channel. Radio messages still pass through mutes, rules, anti-spam, formatting and logging.

Each channel defines Enabled, aliases, an optional permission, its format and listening behavior. A disabled channel is absent from commands, aliases, tab-completion, routing and the centered channel GUI. Switch with /channel <name> and hide an enabled channel with /channel mute <name>.

The trade and auction channel definitions ship with Enabled: false. With Auto_Enable_With_Market_Plugins: true, detecting a compatible external auction plugin activates auction, while a shop plugin activates trade. This runtime activation feeds announcements and the router without enabling Chatalyst's native market. Set the auto option to false to opt out, or set Enabled: true to keep a channel permanently visible.

Chat regions without WorldGuard

The REGION channel type works out of the box: define 3D boxes with /cht region pos1, pos2 and add <name> (persisted in regions.yml), and only players sharing a region hear each other. With WorldGuard installed both sources are merged, so its regions keep working too.

Group overrides

The Groups config section tweaks chat per LuckPerms primary group (Vault fallback): a different chat format (Format, applied only to channels using the base format) and a per-group message delay (Chat_Delay_Seconds, overriding the global anti-spam delay — give VIPs 0 and new players 3, for example).

Exclusive channels

With Channels.Exclusive: true (the default) channels behave like real, separate rooms: besides the default channel — the server's main chat, always audible unless muted with /channel mute — you only receive the channel you are writing in. Being in global hides trade, auction and the rest, and the history replay catches you up when you enter one. Exceptions: /channel listen <name> (a player's explicit read subscription), channels with Force_Listen: true (staff ships with it) and players with chatalyst.channel.seeall. Set Exclusive: false for the classic overlapping behavior where Auto_Listen channels are always visible.

More channel tricks

Shortcut prefixes (Channel_Router.Shortcut_Prefixes): starting a message with a configured prefix ("!selling gold") delivers it to that channel without switching. Region auto-switch: give a chat region a channel (/cht region add mercado trade) and players switch to it on entry and back on exit — manual changes inside the zone are respected. Per-channel Discord (Discord.Channel_Webhooks): each channel can mirror to its own Discord channel via webhook (trade → #market, staff → #staff), taking priority over the global webhook.

Channel history

Each GLOBAL channel keeps a rolling in-memory history (Channels.History): switching channels replays the last messages, clearly marked as already sent ([3m] Name » ...), and /channel history [name] shows it on demand. Frequency, world, region and party channels are never recorded — replaying them would leak messages the viewer was not meant to see. Purged or deleted messages are removed from the history too, and it lives only in memory (cleared on restart).

Smart channel router

The router (Channel_Router in config) keeps global chat free of sale spam: messages written in the default channel that match the configurable Spanish/English patterns ("vendo...", "WTS...", "subasta...") are delivered in their channel automatically — the player is told once a minute, and rules, anti-spam, logging and the delete button keep working because the message follows the normal pipeline. Set Action: block to cancel instead of moving, and grant chatalyst.bypass.router to staff that should never be routed.

Marketplace plugins

Known auction/shop plugins (AuctionHouse, zAuctionHouse, CrazyAuctions, PlayerAuctions, AuctionMaster, QuickShop, ChestShop, ShopGUI+, EconomyShopGUI, DynamicShop and BossShopPro) are detected at startup. Detection auto-enables the relevant integration channel when allowed by that channel's config. With Trade_Plugins.Announce, configured listing commands post localized announcements there with a per-player cooldown, crossing the network when the channel has proxy enabled.

Note

Region and party channels behave like normal channels when WorldGuard or Parties is not installed, so nothing breaks.

Conditional parts

Each part can use Sender_Permission, Sender_Variable or Sender_Condition, plus the matching Receiver_* options. Permissions accept ! negation. Variables support equality, !=, numeric comparisons, containment, lists and bounded regex. JavaScript conditions reuse the restricted compiled-script cache; prefer permissions and variables on busy chat paths.

Sender gates and the component itself are prepared once per message. Only receiver gates run per viewer. Insertion adds shift-click insertion, and the older View_Permission remains an alias of Receiver_Permission.

Placeholders

Built-in: {player_name}, {player_nick}, {player_prefix}, {player_group}, {rank_tag}, {rank_color}, {world}, {ping}, {ping_ms}, {ping_quality}, {ping_bars}, {message}. Any %papi% placeholder works too.

{ping_ms} renders the latency as a number colored by connection quality (23ms in green, 320ms in red) and {ping_quality} as a word (Excellent / Good / Fair / Slow / Laggy) — the default in the chat hover and tab footer. Prefer the classic look? {ping_bars} still draws the colored signal bars (▰▰▰▱▱).

With the Parties plugin, {party} is the player's party name and {party_tag} is the decorated tag styled under Chat.Party_Tag in config. Both resolve to nothing when the player has no party, so the default format shows [RANK] [PARTY] Name » message only for party members.

Players can also type [item] in their message to show the item they are holding, with its full tooltip on hover (permission chatalyst.chat.item, on by default).

Two layers keep chat clean: regex rules and a dedicated swear filter. Both apply everywhere: chat, commands, signs, books, anvils and nicknames.

Rules

Patterns in rules.yml can warn, notify staff, add warning points, replace text or deny the message. Named Groups compose shared settings once at load time, and each rule can override the inherited values. Chatalyst ships with anti-IP, anti-domain and anti-Discord advertising rules and a repeat-character collapser.

Advanced rule options

Every rule also supports: Deny_Silently, Kick, Fine (Vault money), Sound, Title, Actionbar, Bossbar and Toast; Require/Ignore conditions by permission, world, gamemode, channel, region, placeholder value, persistent data or trusted JavaScript predicate; global and per-player delays; and date windows for seasonal rules.

Actions can run console commands, set or remove player state through YAML/SQLite/MySQL, open a configured book, write a dedicated RULE audit event and forward a bounded staff alert to Discord. Rules:

      Variables: {"{player_group}": "in:default,member"}

      Set_Data: {onboarding.step: complete}

The list in swear.yml is multilingual (Spanish, English, Portuguese) and anti-evasion by design. It catches attempts made with repetition, separators and leet-speak, while smart word boundaries stop it from flagging legit words that merely contain a fragment.

# Caught

disputa    hermano    penetrar    computadora

Storage

Nicks, mail, mutes, warnings, reports, channels and settings persist in YAML, SQLite or MySQL — your choice, one key.

Database:
  Enabled: true
  Type: MYSQL
  Host: localhost
  Database: chatalyst
  SSL_Mode: PREFERRED
  Network_Shared: true
  Server_Id: "survival-1"

Normal writes update the in-memory cache immediately and are flushed asynchronously in batches. Operations that must not lose a concurrent change — such as claiming a report or appending network mail — use an immediate database-backed compare-and-set (CAS), retrying against the fresh row when another server wins the race. SSL_Mode controls TLS to MySQL: PREFERRED (default) uses it when the server offers it; use REQUIRED or stronger for any database that is not on localhost.

Network mode

With a shared MySQL across several backends, you decide how data behaves:

Network_Shared: trueNicks, mail, mutes, reports and tickets are network-wide. Atomic counters and conditional updates prevent duplicate report ids and lost read-modify-write transitions. Pair it with Redis sync so caches refresh across servers promptly.
Network_Shared: falseEach server keeps its own data on the same MySQL, separated by Server_Id (auto-named from the port if left empty).
Server_IdGive every backend a stable, unique id. It separates all data when sharing is off and keeps intentionally local stores, such as the market, isolated when sharing is on.

Reliability and backend changes

Failed SQL batches stay queued and are retried; shutdown performs a final synchronous flush. YAML snapshots are written to a temporary file and moved atomically when the filesystem supports it, with a normal replace as fallback, so data is never streamed directly into the live file.

Warning

Changing between YAML and SQL does not import data/*.yml automatically. Back up the server and migrate those values explicitly before changing Database.Enabled / Database.Type. If SQL is unavailable at startup, Chatalyst uses YAML for that run; those fallback changes are not merged into SQL automatically when the database returns.

Troubleshooting

Common issues

The questions that come up most, and the honest technical reasons behind them.

/msg says private messages are disabled

That is the owner's master switch, off out of the box. Set Private_Messages.Enabled: true in config.yml and run /cht reload. Mail (/inbox) works regardless of this switch.

Ranks show no color

Set the LuckPerms prefix with a color code, for example &c[OWNER]. {rank_color} reads the first color from the prefix and paints the name and message to match. Both legacy and MiniMessage prefixes work.

The delete-message X does nothing

Deletion depends on the message, not simply the account mode. Chatalyst can retract a line whenever Paper supplies a SignedMessage.Signature; this has also been verified with nLogin for both premium and non-premium sessions. enforce-secure-profile=true is not a Chatalyst requirement. If the X does not work, that line probably arrived without a usable signature or as system chat, such as a translated per-viewer line. Prevention and auto-mute still work; /clearchat remains the fallback.

All commands show when typing a slash

Since Minecraft 1.13 the client builds that dropdown locally, so the server cannot add a minimum length to command names. Chatalyst hides commands you lack permission for and the info and namespace commands, so the list is as short as possible.

Discord messages do not appear in game

Use the built-in bot: set Discord.Enabled: true, then verify Bot_Token, Guild_Id, Channel_Id, Discord_To_Minecraft and Message Content Intent. Run /chatalyst doctor and check that the bot can view the channel, send messages and read its history. DiscordSRV and chat webhooks are not used.

No name shows above the head

That means the vanilla nametag is hidden (TAB's invisible-nametags or the fancy module's own team) but the fancy nametag is not running. Check that Nametag.Fancy.Enabled is true — it is a different key from the classic Nametag.Enabled, which only does solid team colors and is skipped when TAB is installed. After enabling, /chatalyst reload is enough; the console logs a "Fancy nametags" line when the module starts.

EssentialsX owns a command Chatalyst needs

Chatalyst loads before EssentialsX on purpose and claims the conflicting command names (/msg, /nick, /afk, /me...), leaving Essentials reachable under /essentials:<cmd>. Mail deliberately lives at /inbox so Essentials' /mail (and its command cooldowns) never interfere. No manual config is needed.

The config broke and the server still started

That is the self-healing config: on an unparseable YAML, Chatalyst rescues the license key, backs up the broken file as config-broken-<timestamp>.yml, regenerates the default, and prints the exact error line in the console. Fix your backup, paste your changes back, and run /chatalyst doctor to verify.

Config comments are in Spanish

Configs generated before the English rewrite stay as they were. Delete the YAML files, or set Locale: en_US, to regenerate them in English.

API

Chatalyst provides a versioned Bukkit service, an independent compile-time API jar, durable lifecycle events and PlaceholderAPI values for safe integrations without exposing mutable managers.

Getting the API

The build creates a runtime jar and a smaller compile-time contract. Install Chatalyst-1.0.0.jar on the server; keep Chatalyst-API-1.0.0.jar only in your integration project.

  1. Copy the API jar into your project's libs/ directory.
  2. Declare it as compileOnly (Gradle) or provided (Maven), so it is never bundled or installed as a plugin.
  3. Add Chatalyst to depend when required or softdepend when the integration is optional.
  4. Resolve ChatalystApi in onEnable(), after both plugins are active.
dependencies {
    compileOnly(files("libs/Chatalyst-API-1.0.0.jar"))
}
depend: [Chatalyst]
ChatalystApi api = ChatalystApi.get()
    .orElseThrow(() -> new IllegalStateException("Chatalyst is unavailable"));
TitlesApi titles = api.titles();

TitleProfile profile = titles.profile(player.getUniqueId());
titles.equipped(player.getUniqueId()).ifPresent(title ->
    getLogger().info(title.displayName()));

Titles and achievements service

Definitions, profiles, progress, collections and ranking rows are immutable snapshots. Secret locked titles have no definition in catalogFor, and hidden locked titles are omitted. Administrative catalog intentionally returns the complete configuration.

Handle typed results

Mutation results are machine-readable. Treat SUCCESS and NO_CHANGE as successful, present domain rejections to staff, and log operational failures with their diagnostic message.

TitleMutationResult result = titles.equip(
    player.getUniqueId(), "champion", TitleMutationContext.api());

if (!result.successful()) {
    getLogger().warning(result.status() + ": " + result.message());
}

Evaluate progress safely

Progress reads touch live Minecraft state, so they return futures and run through the player's owning entity scheduler on Paper, Purpur and Folia.

titles.evaluate(player).thenAccept(result -> {
    if (result.successful() && !result.unlocked().isEmpty()) {
        getLogger().info("New titles: " + result.unlocked().size());
    }
});

Lifecycle events

Title state events are emitted only after durable persistence. They carry a TitleMutationContext with the cause, optional actor and reason, and report themselves asynchronous whenever raised outside Bukkit's primary thread.

EventTiming
TitleUnlockEventAfter a new permanent or seasonal unlock is stored
TitleEquipEventAfter a valid unlocked title becomes the durable selection
TitleUnequipEventAfter the selection is removed, including automatic removal on revoke
TitleRevokeEventAfter an existing unlock is removed
TitleCollectionCompleteEventWhen a new durable unlock completes a derived collection
TitleCatalogChangeEventAfter GUI or API creation, update, duplication or deletion is atomically written

The existing ChannelMessageEvent, ChannelSwitchEvent, RuleMatchEvent and RuleReplaceEvent remain available in dev.chatalyst.api.

Listen after persistence

Register ordinary Bukkit listeners. If an event is asynchronous, schedule entity or world access on the correct Bukkit or Folia scheduler.

@EventHandler
public void onTitleUnlock(TitleUnlockEvent event) {
    getLogger().info(event.getPlayerId()
        + " unlocked " + event.getTitle().id());
}
